# Практическое задание 9. Асинхронность и корутины в Kotlin

## Задание 1. Отмена установки приложения

### Реализация
* **Состояния**: В `AppDetailViewModel` используется `InstallState`: `NotInstalled`, `Installing(progress: Int)`, `Installed`.
* **Запуск**: По кнопке «Установить» запускается `installJob = viewModelScope.launch { emulateInstall() }`.
* **Эмуляция**: В цикле от 0 до 100 с шагом 5% и `delay(150)` обновляется `_uiState`. По окончании выставляется `InstallState.Installed`.
* **Отмена**: Пока корутина выполняется, кнопка показывает «Отменить (X%)». Повторное нажатие вызывает `installJob?.cancel()`, что немедленно прерывает `delay()`, выбрасывает `CancellationException` и возвращает состояние в `NotInstalled`.
* **Structured Concurrency**: В `onCleared()` ViewModel вызывается `installJob?.cancel()`, предотвращая фоновые утечки при закрытии экрана.
* **Сохранение состояния**: Идентификаторы установленных приложений сохраняются в `AppRepository`, предотвращая сброс статуса при навигации.

## Задание 2. Загрузка рейтингов в каталоге приложений

### Реализация методов загрузки
Каждый запрос эмулирует сетевую задержку через `delay(1500)`:

1. **Последовательно (`loadRatingsSequentially`)**:
   Запросы выполняются по очереди в цикле `for` через последовательные suspend-вызовы.
2. **Параллельно (`loadRatingsInParallel`)**:
   Запросы запускаются одновременно через `async` внутри `coroutineScope` и ожидаются через `awaitAll()`.

### Результаты замеров времени (`measureTimeMillis`)
Замер проведён на списке из **12 приложений** (10+ элементов) с эмуляцией задержки 1500 мс на запрос:

| Способ загрузки | Кол-во элементов | Задержка 1 запроса | Время выполнения (`measureTimeMillis`) |
| :--- | :--- | :--- | :--- |
| **Последовательно (`for` + `suspend`)** | 12 | 1500 мс | **~18 114 мс (~18.1 сек)** |
| **Параллельно (`coroutineScope` + `async` + `awaitAll`)** | 12 | 1500 мс | **~1 532 мс (~1.5 сек)** |

### Выводы
1. **Производительность**:
    * При последовательном выполнении время суммируется линейно ($12 \times 1.5\text{ с} \approx 18\text{ с}$).
    * При параллельном выполнении все запросы отрабатывают одновременно, общее время равно длительности одного самого долгого запроса ($\approx 1.5\text{ с}$).
    * Получено ускорение **в ~11.8 раз**.
2. **Влияние на UI/UX**:
    * Блокировать интерфейс на 18+ секунд нельзя. Каталог приложений отображается пользователю **мгновенно**, а рейтинги подгружаются параллельно в фоне, появляясь на карточках по мере готовности.
3. **Structured Concurrency (`coroutineScope`)**:
    * Обертка `coroutineScope` связывает все дочерние `async`-задачи. Если родительская корутина отменяется или один из запросов падает с ошибкой, все параллельные задачи автоматически отменяются без утечек памяти и сетевых соединений.
